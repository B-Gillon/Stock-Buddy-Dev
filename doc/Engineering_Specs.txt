# STOCK BUDDY — ENGINEERING SPEC FOR CLAUDE
# Strict, deterministic instructions for generating code, pages, components, and backend logic.

=====================================================================
SECTION 1 — PROJECT OVERVIEW
=====================================================================

Stock Buddy is a Next.js 16.2 application using the App Router (Turbopack). It provides:
- A dashboard
- A Products page
- An Inventory page
- Supplier, Vendor, and Location management
- Purchase Order management (create, detail, receive, cancel)
- A Supabase-backed database
- A Shopify sync pipeline

The project uses:
- React Server Components for data loading
- Client Components for UI interactivity
- Tailwind CSS for styling
- Supabase JS client for database access
- Shopify Admin API for sync

All new code must follow the patterns defined in this document.


=====================================================================

=====================================================================

All files must be placed in the correct folder:

SECTION 4 — SERVER VS CLIENT RULES
=====================================================================

### Server Components (default)
- Used for data fetching
- Used for page-level rendering
- Can import database helpers
- Cannot use state, effects, or event handlers

### Client Components
- Must include: "use client"
- Used for:
    - Modals
    - Tables
    - Filters
    - Buttons
    - Interactive UI
- Can use hooks, state, effects, event handlers

SECTION 7 — SHARED UI COMPONENTS
=====================================================================

Always import shared components from their correct subfolder.
Never import from @/components — use @/shared/components/<subfolder>/.

### Button — @/shared/components/ui/Button
Props: variant ("primary" | "secondary" | "danger"), size ("sm" | "md"),
       onClick, href, disabled, children, type
Default variant: "primary" (blue)
All buttons across the app must use this component.

### Badge — @/shared/components/ui/Badge
Props: status (string key), statusMap (optional override)
Default status map covers PO statuses: draft, released, held,
partially_received, received, cancelled, active, inactive.

### Toast + useToast — @/shared/components/ui/Toast
Named exports: Toast (component), useToast (hook)
useToast returns { toast, showToast }
showToast(message, type?, durationMs?)
Never define inline Toast components in page files — always import.

### Card — @/shared/components/ui/Card
Props: title (optional), children, className, padding ("sm" | "md")
Use for all white rounded bordered content boxes.

### PageHeader — @/shared/components/ui/PageHeader
Props: backHref, backLabel, title, badge, actions
Use for all detail page headers (back button + title + badge + action buttons).

### AppLayout — @/shared/components/layout/AppLayout
Main page wrapper. Used on every page.
Props: title, actions, paginationControls, showActionBar, bareLayout, children

### Header — @/shared/components/layout/Header
Global nav header. Imported by AppLayout only — never import directly.

### SearchModal — @/shared/components/modals/SearchModal
Shared search modal used by list pages.

### SortIcon — @/shared/components/icons/SortIcon
Used in sortable table column headers.

SECTION 11 — SHOPIFY SYNC PIPELINE
=====================================================================

Located in /src/lib/sync/

### Product sync files:
- fetchProducts.js
- processProducts.js
- processVariants.js
- shopifyHelpers.js
- supabaseHelpers.js
- syncProducts.js

### PO sync files (located in /src/lib/sync/po/):
- releasePO.js       — orchestrates PO release: DB update + Shopify incoming push
- receivePO.js       — orchestrates receiving: DB update + Shopify incoming/available adjust
- cancelPO.js        — orchestrates cancellation: DB update + Shopify incoming zero-out
- pushIncoming.js    — pushes incoming qty to Shopify on release (idempotent)
- poSyncHelpers.js   — shared utilities: Shopify API calls, DB logging, credential resolution

### PO sync rules:
- Stock Buddy is the canonical PO system
- Shopify is the canonical inventory system
- Never create or edit Shopify POs — only sync effects (incoming, available, metafields)
- All Shopify calls are scoped by tenant credentials
- po_shopify_incoming table tracks every push for idempotency and reversal
- releasePO rolls back DB status if Shopify push fails
- receivePO does NOT roll back DB on Shopify failure (received qty is ground truth)


=====================================================================
SECTION 12 — PO LIFECYCLE
=====================================================================

Status values (always lowercase):
  draft → released → partially_received → received
                   ↘ cancelled (from released or partially_received)

Timestamps:
- released_at     — set on release
- received_at     — set when fully received
- cancelled_at    — set on cancel
- shopify_synced_at   — set after successful Shopify sync
- shopify_sync_error  — last error message if sync failed

### On Release:
1. Validate status === "draft"
2. Update status → "released", set released_at
3. Push incoming quantities to Shopify via pushIncoming.js
4. Write PO metafields to Shopify inventory items
5. Log to po_shopify_incoming
6. Stamp shopify_synced_at

### On Receive:
1. Validate status in ["released", "partially_received"]
2. Update purchase_order_lines.received_qty_units
3. Recalculate PO status (partially_received or received)
4. Adjust Shopify: decrease incoming, increase available
5. Mark po_shopify_incoming rows as reversed

### On Cancel:
1. Update status → "cancelled", set cancelled_at
2. Zero out remaining incoming in Shopify
3. Mark po_shopify_incoming rows as reversed

SECTION 16 — TENANT RESOLUTION ARCHITECTURE
=====================================================================

Two helpers in /src/lib/tenants.js handle tenant resolution:

getTenantId(request)
- For use in API routes
- Reads x-shop-domain from a Request object
- Falls back to NEXT_PUBLIC_DEV_SHOP_DOMAIN and DEV_SHOP_DOMAIN env vars in dev
- REMOVE fallbacks before going to production

getTenantIdFromHeaders(headersList)
- For use in server components
- Reads from Next.js headers() result (import { headers } from 'next/headers')
- Falls back to NEXT_PUBLIC_DEV_SHOP_DOMAIN and DEV_SHOP_DOMAIN env vars in dev
- REMOVE fallbacks before going to production

supabaseAdmin in /src/lib/supabaseAdmin.js
- Uses SUPABASE_SERVICE_ROLE_KEY
- Bypasses RLS — used only for tenant lookups and infrastructure code
- Never use for tenant-scoped data queries

Usage pattern in server components:
  const headersList = await headers();
  const tenantId = await getTenantIdFromHeaders(headersList);

Usage pattern in API routes:
  const tenantId = await getTenantId(request);

SECTION 19 — SUPPLIER DETAIL PAGE PATTERNS
=====================================================================

The supplier detail page uses an inline tab pattern where tabs appear
on the same row as the back button and supplier name/number.

Current tabs:
1. General Info   — top row of info cards (read-only)
2. Product Data   — associated products table
3. CSV Overrides  — per-supplier CSV field toggles
4. Transmission   — PO email recipient table

CSV Overrides tab behavior:
- Loads global CSV settings from /api/settings
- Loads supplier-specific settings from /api/suppliers/[id]/csv-settings
- Auto-saves on every toggle change (no Save button)
- Auto-switches to Supplier-Specific mode when any toggle is changed
- use_global flag stored in supplier_csv_settings.use_global column
- Settings stored in supplier_csv_settings table (one row per supplier,
  one boolean column per CSV field)

Transmission tab behavior:
- Loads recipients from /api/suppliers/[id]/transmission
- Explicit Save button (batch save — delete + re-insert all rows)
- Save button disabled until a change is made
- Validates at least one Primary recipient with email before saving
- Each recipient has: label, email, role (Primary/CC/BCC), send_pdf, send_csv
